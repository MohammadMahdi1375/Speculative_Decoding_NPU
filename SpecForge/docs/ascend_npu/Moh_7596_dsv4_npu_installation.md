# SpecForge on Ascend NPU — V4-Flash SGLang Backend Installation Guide

> Reproducible install for SpecForge **DFlash with the SGLang target-model
> backend** on Ascend NPU (Atlas A2 / 910b), targeting the
> **DeepSeek-V4-Flash** model family. This is the V4 NPU port from the
> `feat/dsv4-npu` branch.
>
> If you only need the HF target-model backend (no V4 kernels, no sglang),
> use [`Moh_7596_installation.md`](./Moh_7596_installation.md) instead.

---

What this install **does not** include (deliberately):
- The stub model safetensors (~329 MB) — **regenerated by `prepare_dsv4_stub_target.py`** on first install
- The built `*.whl` files (platform-specific; built per-server via `build.sh`)
- `tilelang-ascend` source (~1 GB git repo with submodules; cloned separately during install)
- Random-init weights from training — checkpoints stay on disk, not in git

## Caveats — what works, what doesn't

| Workflow | Status |
|---|---|
| SpecForge DFlash training data generation (prefill-only) | ✅ Works on the V4 stub |
| Inference prefill (single forward) | ✅ Works |
| Inference decode (autoregressive, multi-step) | ❌ Not implemented (KV cache is no-op stubs) |
| Real V4 (head_dim=512) using `npu_sparse_flash_attention` kernel | ⚠️ Kernel path wired, untested without real V4 weights |
| Multi-NPU TP/EP (>1 NPU) | ⚠️ Smoke-tested at TP=1; multi-NPU untested |

**Loss is `nan` on the stub.** This is expected — stub weights are random and MoE/MTP heads aren't wired through the reference attention. The point of the smoke test is to verify the forward+backward pass runs end-to-end, not that loss decreases.

### Step 0 — Source CANN

```bash
export CANN_HOME=/path/to/your/CANN/8.5.x         # ← edit for your install
export ASCEND_HOME_PATH=$CANN_HOME                # required by sgl-kernel-npu/build.sh
source "$CANN_HOME/ascend-toolkit/set_env.sh"
[ -f "$CANN_HOME/nnal/asdsip/set_env.sh" ] && source "$CANN_HOME/nnal/asdsip/set_env.sh"
[ -f "$CANN_HOME/nnal/atb/set_env.sh" ]    && source "$CANN_HOME/nnal/atb/set_env.sh"

# Sanity check
echo "ASCEND_HOME_PATH=$ASCEND_HOME_PATH"
which msopgen   # should be inside $ASCEND_HOME_PATH/bin
```

```bash
mkdir -p ~/specforge_v4 && cd ~/specforge_v4

source "$(conda info --base)/etc/profile.d/conda.sh"
conda activate ./conda/specforge_npu
```


### Step 4 — Install sglang from source (`v0.5.9` + NPU pyproject)

**Required even though we use the sglang fork in this repo** — sglang has C-extension
modules that must be installed via pip before our fork's Python sources can be imported.

Follow [HF guide Step 4](./Moh_7596_installation.md#step-4--install-sglang-required-even-for-hf-backend) in full:
1. **4a** — Install Rust via conda
2. **4b** — Configure cargo with Huawei mirror (git-protocol, not sparse)
3. **4c** — Clone sglang upstream and swap to `pyproject_npu.toml`
4. **4d** — `pip install -e "python[srt_npu]"` with PyPI fallback
5. **4e** — Pin `setuptools==80.9.0` (catches the `pkg_resources` issue early)

After the upstream sglang install completes, **point Python at our fork's sources**:

```bash
cd $SPECFORGE_ROOT
pip install -e ./sglang/python --no-deps
```

This makes `import sglang` resolve to OUR patched sources, not upstream.

### Step 5 — Build and install the V4-capable sgl-kernel-npu wheels

The workspace `sgl-kernel-npu/` in this branch ships:
- All V4 op sources in `csrc/` (`lightning_indexer`, `attentions`, `batch_matmul_transpose`, `mla_preprocess`, `catlass`, etc.)
- Patched `build.sh` (respects `$ASCEND_HOME_PATH`; skips `deepep` when `-a kernels` is used)
- Submodule content for `third-party/pto-isa/` (pre-populated, no `git submodule init` needed)

The build *just works* — no manual patching or upstream cloning required.

```bash
cd $SPECFORGE_ROOT/sgl-kernel-npu

# CRITICAL: CANN's msopgen rejects input files with group/world write permissions.
# Some umask settings (002, common on multi-user nodes) clone files as 664.
# Strip group/world write across the source tree before building:
chmod -R go-w .

# Build kernels + attentions (deepep is auto-skipped by our patched build.sh)
bash build.sh -a kernels Ascend910B1     # SOC for Atlas A2 / 910b

# Built wheels appear in output/
ls output/*.whl
# Expected:
#   sgl_kernel_npu-2026.X.Y-cp311-cp311-linux_aarch64.whl
#   attentions-0.X-cp311-cp311-linux_aarch64.whl

# Install them into the conda env
pip install --force-reinstall --no-deps output/sgl_kernel_npu-*.whl
pip install --force-reinstall --no-deps output/attentions-*.whl

# CRITICAL: the `attentions` library has a runtime permission check on its
# installed .so files — it rejects anything with permissions higher than 0o755.
# pip on some systems installs them as 0o775 by default. Strip the excess:
chmod -R go-w $CONDA_PREFIX/lib/python3.11/site-packages/attentions/
chmod -R go-w $CONDA_PREFIX/lib/python3.11/site-packages/sgl_kernel_npu/

# Verify the install worked
python -c "
import sgl_kernel_npu as k
import attentions as a
print('sgl_kernel_npu:', k.__path__[0].split('/')[-1])
print('attentions loaded:', a.__file__)
print('attentions ops:', [x for x in dir(a) if not x.startswith('_')])
"

cd $SPECFORGE_ROOT
```

If anything fails, see [Troubleshooting V8](#v8-permissionerror-on-libptaextensionopsso).

### Step 6 — Install `tilelang-ascend`

`tilelang-ascend` provides the AscendC backend for tilelang kernels used by
SGLang's MHC Sinkhorn (we override most of these with PyTorch fallbacks via
env vars, but the module must still import cleanly). It's not bundled in
the branch (~1 GB with submodules); clone and install from upstream:

```bash
mkdir -p $SPECFORGE_ROOT/third_party
cd $SPECFORGE_ROOT/third_party
git clone --recursive https://github.com/tile-ai/tilelang-ascend.git
cd tilelang-ascend
git checkout ascendc_pto      # branch known to work with CANN 8.5.x
git submodule update --init --recursive

# Install (editable; uses the tilelang build system to produce a working module)
pip install -e . --no-deps

cd $SPECFORGE_ROOT
```

Verify:
```bash
python -c "import tilelang; print('tilelang', tilelang.__version__)"
# Expected: tilelang 0.1.4+ubuntu.22.3.cann851 (or similar with cann851 tag)
```

If you'd rather use a pre-built wheel and have access to one (e.g. from
the original build server), just `pip install <path-to-wheel>` instead.

### Step 7 — Create the Triton `cann` extension stub

`sgl_kernel_npu` 2026.5.x eagerly imports `triton.language.extra.cann.extension`,
but `triton-ascend` 3.2.0 names its NPU backend module `triton.language.extra.ascend`.
To bridge the gap without patching either package, create a minimal stub:

```bash
TRITON_EXTRA="$(python -c 'import triton.language.extra as e, os; print(os.path.dirname(e.__file__))')/cann"
mkdir -p "$TRITON_EXTRA"

cat > "$TRITON_EXTRA/__init__.py" <<'PY'
"""Compatibility stub: sgl_kernel_npu expects triton.language.extra.cann
but triton-ascend exposes triton.language.extra.ascend. Importers get a
module; any attribute access raises NotImplementedError, which sgl_kernel_npu
catches and falls back from."""
from importlib import import_module as _imp

def __getattr__(name):  # PEP 562 — lazy attribute
    if name == "extension":
        return _imp("triton.language.extra.cann.extension")
    raise AttributeError(f"triton.language.extra.cann has no attribute {name!r}")
PY

cat > "$TRITON_EXTRA/extension.py" <<'PY'
"""Stub for triton.language.extra.cann.extension.
sgl_kernel_npu imports this module at top level. None of the wrapper code
that imports it is reached on NPU paths we exercise, so we just need the
module to import cleanly and any attribute access to raise."""
def __getattr__(name):
    raise NotImplementedError(
        f"triton.language.extra.cann.extension.{name} is a CUDA Triton "
        "shim; on NPU it's unreachable via SGLang's import path."
    )
PY

python -c "import triton.language.extra.cann.extension; print('cann stub OK')"
```

Expected output: `cann stub OK`.

## Required environment variables (V4-specific)

The launch script sets sensible defaults, but if running training scripts
directly, you must set these:

| Variable | Required value | Why |
|---|---|---|
| `SPECFORGE_ATTENTION_BACKEND` | `dsv4` | Selects `DeepseekV4AscendAttnBackend`. Use `ascend` for non-V4 NPU models. |
| `SGLANG_OPT_BF16_FP32_GEMM_ALGO` | `torch` | Forces torch matmul path; the NPU lacks the CUDA-only GEMM kernels SGLang prefers |
| `SGLANG_OPT_USE_TILELANG_MHC_PRE` | `False` | Disables CUDA-only MHC pre-norm tilelang kernel; falls back to PyTorch Sinkhorn |
| `SGLANG_OPT_USE_TILELANG_MHC_POST` | `False` | Same for post-norm |
| `SGLANG_OPT_DEEPGEMM_HC_PRENORM` | `False` | Disables DeepGEMM (CUDA-only) for H-compression pre-norm |
| `SGLANG_NPU_DISABLE_ACL_FORMAT_WEIGHT` | `True` | Skips ACL_FORMAT weight conversion — incompatible with our stub layer shapes |
| `ASCEND_HOME_PATH` | path to CANN | Required by sgl-kernel-npu runtime |
| `ASCEND_LAUNCH_BLOCKING` | `1` (debug) / `0` (perf) | Set to 1 only when chasing NPU crashes — slows training ~10× |

Optional:
| Variable | Default | Purpose |
|---|---|---|
| `TILELANG_ASCEND_EXAMPLES_DIR` | bundled path | Override the tilelang-ascend examples directory if you move the source tree |

## Troubleshooting

### V4-specific

#### V1. `qk_head_dim only support 512`

The `npu_sparse_flash_attention` kernel hard-requires `qk_head_dim=512` (nope=448
+ rope=64), matching the real DeepSeek-V4-Flash architecture. The stub uses
`qk_head_dim=128` (96+32), which is below the kernel's hard constraint.

The V4 backend detects this and falls back to a PyTorch reference attention
path — **this is expected on the stub**. The fallback is correct for training
data prep (prefill-only) but won't exercise the actual NPU kernel.

To exercise the kernel path, you need a target with `qk_head_dim=512` —
either real DeepSeek-V4-Flash weights, or a custom-sized stub with full V4
head dimensions.

#### V2. `attentionMode only support 2`

The kernel accepts `attentionMode ∈ {0, 1, 2}` but on NPU only mode 2 is
implemented. Mode 2 = MLA + RoPE applied together. The V4 backend always
passes mode 2 — if you see this error from upstream code, it means a call
site bypassed our backend. File a bug with the call site path.

#### V3. `CUDA_HOME environment variable is not set`

Triggered by SGLang's `_dispatch_bf16_fp32_backend` when MoE gating runs.
Our patch in `sglang/python/sglang/jit_kernel/deepseek_v4.py` short-circuits
this on NPU. If you still see it:
- Confirm `sglang` is installed editable from THIS branch (not upstream):
  `pip show sglang | grep Location` should point at `<repo>/sglang/python`
- Confirm the patch is present: `grep -n "torch.npu.is_available" sglang/python/sglang/jit_kernel/deepseek_v4.py`

#### V4. `'DeepseekV4AscendAttnBackend' object has no attribute 'forward_compress'`

**Cosmetic warning, training proceeds.** The V4 Compressor module calls
`forward_compress`; we stub this as no-op in our backend, and the warning
is logged when the compressor swallows the AttributeError. To silence,
implement `forward_compress` as a real no-op method in `dsv4_ascend_backend.py`.

#### V5. MTP feature-dim mismatch

If you see `RuntimeError: ... expected 1024, got 4096` during the loss
computation, it's the MTP (Multi-Token Prediction) hidden-state slicing.
DeepSeek-V4-Flash concatenates MTP layers in the last dim:
`hidden_states.flatten(1) → [T, num_mtp × hidden]`.

Our bridge in `dflash_target_model.py` slices out the requested
`target_layer_ids`. If you're training with a different `target_layer_ids`
config, verify the slicing math is correct for your case.

#### V6. Loss is `nan` from step 1

**Expected on the stub.** The stub model has random-init weights; MoE expert
weights are random; the draft can't learn anything useful from random target
hidden states. The smoke test verifies *the training loop runs*, not that
loss is meaningful.

For real loss curves, point `TARGET_MODEL` at actual DeepSeek-V4-Flash weights.

#### V7. `npu_sparse_flash_attention` segfault during a real training run

On stub configs we fall back to PyTorch reference, so the kernel isn't called.
On real V4 configs the kernel path is exercised but **untested in this branch**.
If you see a crash, capture the stack trace with `ASCEND_LAUNCH_BLOCKING=1`,
report which layer (sliding/CSA/HCA) it crashed in, and check the kernel
arg shapes match the upstream contract.

#### V8. `PermissionError` on `libPTAExtensionOPS.so`

**Full error**:
```
PermissionError: The permission of .../attentions/plugin/libPTAExtensionOPS.so
is higher than 0o755.
```

The `attentions` library refuses to load any installed library file with
group/world write permission. pip on some systems installs files with 775
permissions when the umask is permissive.

**Fix**:
```bash
chmod -R go-w $CONDA_PREFIX/lib/python3.11/site-packages/attentions/
chmod -R go-w $CONDA_PREFIX/lib/python3.11/site-packages/sgl_kernel_npu/
```

This is also covered in Step 5 — re-run those `chmod` commands any time
you re-install the wheels.

#### V9. Build fails with `Detected CANN Toolkit Installation Path: /home/<otheruser>/CANN_...`

Stale upstream `build.sh` symptom — the script reads `/etc/Ascend/ascend_cann_install.info`
which on multi-user nodes points at another user's CANN install. The branch's
patched `build.sh` honors `$ASCEND_HOME_PATH` first; if you still see this:

- Confirm you're running the patched `build.sh`: `grep -c "Moh_7596" sgl-kernel-npu/build.sh` should be ≥ 2
- Confirm `$ASCEND_HOME_PATH` is exported and points at a directory you own: `ls -la $ASCEND_HOME_PATH`

#### V10. Build fails with `AddCustom.json should not be written by user group or others`

CANN's `msopgen` rejects input files with group/world write. Your shell's umask
created them as 664.

**Fix**:
```bash
cd $SPECFORGE_ROOT/sgl-kernel-npu
chmod -R go-w .
bash build.sh -a kernels Ascend910B1
```

Step 5 includes this `chmod` before the build for exactly this reason.

## What's NOT implemented (production gaps)

For a production-grade V4 NPU port, these still need work:

1. **KV cache write paths** — `store_cache`, `forward_core_compressor`,
   `forward_c4_indexer`, `forward_compress` are all no-op stubs. Works for
   prefill-only (SpecForge data-prep); breaks for inference decode.

2. **Real `npu_sparse_flash_attention` kernel path** — wired but only
   exercised at `head_dim=512` (real V4); untested without real weights.

3. **Multi-NPU TP/EP** — smoke-tested at TP=1; multi-NPU paths untested.

4. **Decode mode** — every method that touches the KV pool is a no-op,
   so autoregressive generation will crash. Use HF backend
   ([`Moh_7596_installation.md`](./Moh_7596_installation.md)) for inference.

See `SpecForge/docs/dsv4_npu_port/` (in this branch) for the design notes
and CUDA reference code used during the port.
